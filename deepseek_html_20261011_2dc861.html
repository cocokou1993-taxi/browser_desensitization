1. 产品定位

一个本地处理、不上传、不联网、无遥测的敏感词检测与脱敏工具。

  • 唯一实现形态：Chrome 浏览器插件（Manifest V3）。
  • 处理边界：本地规则检测与本地脱敏，不对接大模型或云端服务。
  • 词库共享：JSON 文件手动拷贝，适合个人与小团队。
  • 目标用户：个人开发者、小团队，统一词库、无需审计。
设计原则：可编译运行优先 > 完全脱敏；原文件不修改；关闭即不处理。

3. 浏览器插件功能

插件核心功能为 A、C、D 三项；检测、匹配、替换和文件解析均在插件本地完成，不调用大模型或远程接口。

A. 网页输入框 / 剪贴板脱敏

  • 检测页面输入框、文本域、可编辑区域。
  • 提供「脱敏复制」「脱敏替换」两种动作。
  • 插件关闭时不处理、不注入、不拦截。

C. 上传文件前脱敏

  • 检测文件上传控件、拖拽上传区域。
  • 本地解析文件并生成脱敏副本。
  • 默认提示用户确认后上传或下载副本，不静默替换。
  • 输出文件名：原文件名.redacted.ext。

D. 内置本地脱敏工作台

  • 支持粘贴文本或拖拽文件，本地脱敏后复制或下载。
  • 不对接大模型，D 已定义为「本地脱敏工作台」，不提供聊天或远程推理能力。

总开关

状态行为
插件打开启用拦截与脱敏
插件关闭所有页面不处理、不注入、不拦截

4. 词库与匹配规则

4.1 词库

  • 格式：JSON。
  • 内置：政治合规词库，可新增。
  • 自定义：API Key、手机号、身份证、邮箱、公司名、商业机密、其他敏感词。
  • 白名单：人工维护。
  • 共享方式：手动拷贝 JSON 文件，无云端同步。

4.2 匹配能力（第一版）

  • 正则表达式
  • 大小写不敏感
  • 全半角归一
  • 分组、分级、优先级

4.3 优先级

  1. 政治敏感词（最高）
  2. 白名单
  3. 普通敏感词、正则、公司名、商业机密等
待确认：政治敏感词命中时，白名单是否也不能豁免？当前按「不能豁免」处理。

6. 文件与代码处理

6.1 办公与文本文件

  • 第一版支持：docx、xlsx、md、txt、csv、xml、yml、sql。
  • 输出格式与输入一致。
  • 不覆盖原文件。

6.2 代码文件

  • 处理语言范围：英文与中文。
  • 字符串、注释：直接替换。
  • 标识符：安全重命名并同步引用。
  • 无法保证编译运行时，提示人工确认。
  • 第一版支持的代码语言待确认（如 JS、TS、Python、Java、Go）。

8. 验收标准

  1. 插件开启时，输入框 / 剪贴板脱敏生效；关闭时不处理。
  2. 上传 docx / xlsx 前可生成本地脱敏副本，格式基本保留。
  3. md、txt、csv、xml、yml、sql 正确脱敏。
  4. 代码字符串、注释、标识符按规则处理，尽量可编译运行。
  5. 政治敏感词优先级最高，白名单规则符合确认结果。
  6. 输出文件名 .redacted.ext，不覆盖原文件。
  7. 运行时无网络请求，无遥测。
  8. 大模型接入、远程调用和可逆还原被明确排除；所有检测与替换结果均由插件本地生成。
  9. 支持 UTF-8、GBK 编码。

第一轮 · 需求初步理解与边界

目标：确认产品形态、用户、敏感范围、词库、脱敏方式、格式优先级、本地边界、输出、平台。

Q1：产品形态优先做哪种？
A：初步讨论为 CLI + 浏览器插件；后续已收敛为仅实现 Chrome 浏览器插件（见 Q28）。
Q2：目标用户与是否需要统一词库、审计？
A：个人与小团队；需要统一词库；不需要审计。
Q3：敏感内容范围？
A：手动维护白名单、API Key、手机号等 PII、政治合规词库、商业机密。
Q4：词库与规则能力？
A：支持全部能力（正则、分组分级、优先级、白名单、大小写 / 全半角 / 简繁 / 变体 / 拼音 / 谐音）；白名单人工维护；政治敏感词内置且可新增。
Q5：脱敏方式？
A：按内容区分——手机号保留长度掩码；公司名与敏感词替换为 ***；不接入大模型，不做可逆还原扩展。
Q6：文件格式优先级？
A：优先 docx / doc / xls / xlsx / md / txt / csv / xml / yml / sql；其次 PDF、压缩包、扫描识别文件。
Q7：编程场景边界？
A：处理全文；脱敏后仍需可编译运行；不扫描 Git；不接 CI/CD。
Q8：本地处理边界？
A：绝对不联网；词库手动导入更新；禁止遥测。
Q9：输出与审计？
A：输出格式匹配输入；流进流出，文件进文件出；不做审计、不出报告。
Q10：平台与性能？
A：先支持 Windows 与浏览器插件。

附录 B：架构决策记录（ADR）

以下 ADR 记录本轮讨论中已确认的关键架构与策略决策。状态为「已接受」的表示双方已确认；「待定」的表示仍需业务方最终拍板。

已接受

ADR-001：仅实现 Chrome 浏览器插件，不做 CLI

背景
最初设想为 CLI + 浏览器插件双形态，但需求后续要求只交付浏览器插件。
决策
只实现 Chrome 浏览器插件；CLI、桌面客户端和云端服务均不实现。
理由
浏览器插件能覆盖剪贴板、输入框、上传前脱敏等高频办公场景，落地快且能严格限制在本地方案内。
影响
不做批量并发；插件内单次处理一个文件。
已接受

ADR-002：运行时绝对不联网，禁止遥测

背景
敏感文件与词库不能离开本地，用户对数据外泄风险高度敏感。
决策
插件运行时禁止任何网络请求与遥测上报；仅插件更新允许联网。
理由
零网络请求是最强隐私保证，也便于通过企业安全审查。
影响
不能用云端词库同步、云端 NER、云端 OCR；词库共享必须手动拷贝 JSON。
已接受

ADR-003：词库采用本地 JSON，手动拷贝共享

背景
小团队需要统一词库，但禁止联网排除了云端同步方案。
决策
词库以 JSON 文件本地存储；团队通过手动拷贝同一份 JSON 实现共享。
理由
JSON 可读、可版本管理、可人工审查；无需服务端。
影响
需要定义清晰的 JSON Schema 与版本号字段；词库冲突需人工处理。
已接受

ADR-004：词库通过本地 JSON 手动导入导出

背景
可选方案包括本地服务、Native Messaging 和手动文件导入导出。
决策
采用「手动导入同一份词库文件」方案。
理由
无网络请求、无本地服务、实现简单，符合离线约束。
影响
词库更新后需用户手动重新导入；不提供跨工具实时同步。
已接受

ADR-005：优先级为「政治敏感词 > 白名单 > 普通敏感词」

背景
白名单与政治敏感词可能冲突，需要明确谁优先。
决策
政治敏感词优先级最高，其次白名单，最后普通敏感词、正则、公司名与商业机密。
理由
政治合规属最高风险等级，不允许被白名单豁免。
影响
命中政治词时直接脱敏，白名单不生效；需在引擎中实现分级短路逻辑。
已接受

ADR-006：脱敏策略按内容类型区分，而非统一替换

背景
统一替换为 *** 会破坏可读性与部分业务可用性。
决策
手机号、身份证、邮箱保留长度掩码；API Key 与政治敏感词逐字符替换为 *；公司名、商业机密与普通敏感词替换为 ***。
理由
在保护隐私的同时，尽量保留格式与可读性。
影响
需要按规则配置掩码类型（phone / idcard / email / char / star3）。
已接受

ADR-007：第一版文件格式范围为 docx / xlsx / md / txt / csv / xml / yml / sql

背景
格式支持成本差异大，PDF、旧版 Office、压缩包解析复杂。
决策
第一版支持 docx、xlsx、md、txt、csv、xml、yml、sql；排除 doc、xls、PDF、压缩包、扫描件。
理由
这些格式覆盖绝大多数办公与开发日常场景，且解析库成熟。
影响
PDF 重排、OCR、压缩包递归等能力放到后续版本。
已接受

ADR-008：代码脱敏以「可编译运行优先」，标识符安全重命名

背景
直接把标识符替换为 *** 会导致语法错误、无法编译。
决策
字符串与注释直接替换；标识符命中时安全重命名并同步引用；无法安全处理时提示人工确认。
理由
保证脱敏后代码仍可编译运行，避免破坏开发流程。
影响
需要按语言实现作用域分析与引用同步；第一版需明确支持的语言清单。
已接受

ADR-009：不对接大模型，不做可逆还原

背景
可逆映射涉及映射表生命周期、多轮对话、流式返回等复杂问题。
决策
不接入大模型，不实现请求掩码、返回反向替换和可逆还原。
理由
聚焦核心脱敏能力，降低第一版复杂度。
影响
脱敏结果保持一次性输出，不维护映射表，降低数据残留和还原风险。
已接受

ADR-010：文本流式处理，二进制文件走文件路径

背景
Office 等二进制格式无法简单流式处理。
决策
文本类支持流进流出；docx、xlsx 等二进制文件走文件输入输出。
理由
匹配真实使用场景，降低实现复杂度。
影响
插件内文本在工作台或输入框处理；二进制文件按本地副本生成。
已接受

ADR-011：输出不覆盖原文件，命名 原文件名.redacted.ext

背景
脱敏结果需要可追溯、可回滚。
决策
默认另存为 原文件名.redacted.ext，不修改原文件。
理由
避免误操作导致原始数据丢失。
影响
批量处理时需处理同名冲突策略（后续确认）。
已接受

ADR-012：插件关闭时零注入、零拦截

背景
用户可能只想在特定场景启用脱敏，而非全程拦截。
决策
插件关闭时不注入脚本、不拦截请求、不处理任何页面内容。
理由
尊重用户控制权，降低对正常浏览的干扰。
影响
需要明确的总开关状态管理与页面注入时机。
已接受

ADR-013：编码支持 UTF-8 与 GBK，单文件处理

背景
Windows 环境下 GBK 文件仍常见，需兼容。
决策
支持 UTF-8 与 GBK；单次任务一次处理一个文件。
理由
覆盖主流中文编码；并发上限兼顾性能与稳定性。
影响
需做编码探测与回退策略；并发能力不在本方案范围。
已接受

ADR-014：不做审计、报告、Git 扫描与 CI/CD 集成

背景
目标用户为个人与小团队，无合规审计诉求。
决策
第一版不实现审计日志、命中报告、Git 仓库扫描、CI/CD 集成。
理由
减少范围，聚焦核心脱敏体验。
影响
不在插件中展示审计报告，也不提供退出码类批处理接口。
已接受

ADR-015：D 功能定义为「本地脱敏工作台」而非「内置聊天窗口」

背景
用户确认插件包含 A、C、D 三项功能，其中 D 原描述可能为内置聊天窗口。
决策（建议）
D 定义为「本地脱敏工作台」：粘贴文本或拖拽文件，本地脱敏后复制或下载。
理由
与「不对接大模型、不做可逆还原」的决策一致，避免引入不必要的聊天与网络能力。
影响
不添加聊天会话、远程推理和模型接入；后续如需这些能力应另立方案。
待定

ADR-016：政治敏感词命中时白名单不豁免

背景
优先级已定为「政治敏感词 > 白名单」，但未明确政治词是否可被白名单豁免。
决策（建议）
政治敏感词命中即脱敏，白名单不生效。
理由
政治合规为最高风险等级，应保持绝对优先级。
影响
引擎需实现「政治词短路」逻辑，白名单校验在其后执行。
待定

ADR-017：上传前脱敏采用「用户确认后上传 / 下载」而非静默替换

背景
上传控件行为差异大，静默替换存在误操作与数据丢失风险。
决策（建议）
检测到上传时弹出确认，用户选择上传脱敏副本或下载脱敏副本。
理由
透明可控，避免误替换原始上传内容。
影响
需要设计插件弹窗交互与文件替换策略。
待定

ADR-018：第一版代码文件支持语言清单

背景
代码脱敏需要按语言实现语法解析与引用同步，语言数量直接影响工作量。
决策（建议）
第一版优先支持 JS / TS、Python、Java、Go 四类；其余语言按文本规则处理字符串与注释。
理由
覆盖主流开发场景，同时控制解析器实现成本。
影响
需引入或自研轻量解析器；未支持语言的标识符命中走人工确认。
待定

ADR-019：插件更新方式

背景
Chrome 商店自动更新与开发者模式手动加载，影响分发与合规审查。
决策（建议）
第一版以开发者模式手动加载为主，稳定后上架 Chrome 商店。
理由
早期迭代快，便于小团队内部试用。
影响
需明确更新频率与版本号规范。
